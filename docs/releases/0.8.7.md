# 0.8.7 Codex platform compatibility

This patch restores the native platform paths that record-based admission in
0.8.6 did not cover. Standard npm and pnpm launchers are resolved through package
metadata to the native executable. Council does not execute the launcher scripts.
Windows uses PE validation, rejects reparse points in the runtime copy, preserves
the OS loader path and isolates user directories. Read-only snapshot files are
removed after the request. Windows sharing violations are retried within one
second; persistent locks still report incomplete cleanup.

The existing security boundary remains: processes running as the same OS user
are trusted. Every runtime file must match the maintained compatibility record,
and the same private copy is used for the whole request. Selected authentication,
tool suppression, output validation, deadlines and cleanup remain required.
Windows retains its existing direct-child termination behavior; POSIX retains
process-group termination. No new runtime dependency or saved configuration is
required.

## What an upgrade does

Council resolves the selected installation, finds a current record for its
platform and request context, verifies a private copy, then checks its version
and bundled model catalog. A compatible Codex upgrade can be enabled by a
reviewed record update without releasing Council. An unknown build or context
fails closed. A real protocol change can still require an adapter update.

An explicit Council model takes precedence. Otherwise Council uses the model
selected in Codex configuration. No model or cost is chosen automatically.

## Verification matrix

- Linux x86-64, Codex 0.162.1: all 44 runtime files matched the official npm
  artifact. Four live ChatGPT requests passed on Hermes using `gpt-6.1-sol`:
  default/high reasoning with text/JSON schema output.
- macOS ARM64, Codex 0.165.0: the Mac mini completed a full Council request with
  explicit `gpt-6.1-sol` on the published 0.8.6 package. The prior error was its
  configured model being absent from the record, not changed runtime files.
- The local macOS ARM64 native probe passed all 18 synthetic cases under an
  OS-enforced loopback-only network policy. It covered ChatGPT, API-key and
  custom API-key routes with `gpt-6.1-sol`.
- Native CI qualification for macOS, Linux and Windows on ARM64 and x86-64 is
  pending. Do not interpret the new matrix as a successful run until its results
  are recorded here.

The native workflow uses official npm packages, synthetic authentication and a
TLS loopback response server on disposable GitHub runners. It checks text/JSON,
default/high reasoning, authentication routing, no advertised tools, rejection
of unsolicited shell/patch calls, and removal of private runtime/authentication
directories. Its record artifact is written only after all checks pass. The
workflow does not claim to impose an OS network sandbox or prove real provider
access. Host tests and synthetic qualification are separate evidence.

## Review and dependency limits

The attempted three-provider Council review did not complete: Vertex produced an
empty draft, OpenRouter failed at the network layer, and its attached diff was
truncated. Retries were stopped. An independent `gpt-6.1-sol` review approved the implementation; no Council
approval is claimed.

Runtime dependencies and their selected lockfile versions are unchanged from
0.8.6. A verified-TLS OSV query on 2026-10-29 returned no matches for these selected
installed public direct dependencies: Pydantic 2.14.2, HTTPX 0.28.1, AnyIO 4.15.1,
Certifi 2026.10.23, Typer 0.27.3, Rich 15.0.0, PyYAML 6.0.3, JSONSchema 4.26.0,
aiosqlite 0.22.1, Anthropic 2.3.0, OpenAI 3.41.0, Google GenAI 2.34.0,
Google Auth 2.62.0 and urllib3 2.8.0. CVE Now was unavailable. This check does not
cover the complete transitive tree or runtime advisories and is not a security
clearance.
